## What WSYATM is

A Firebase-hosted movie-engagement platform for theater lobbies:

- **frontend/** — React 19 + Vite + TypeScript + Tailwind (its own package.json).
- **functions/** — Firebase Cloud Functions (Node 22, CommonJS). Each endpoint is an
  `onRequest({cors:true}, …)` export; URL routing via `firebase.json` rewrites.
  Auth is a hand-rolled `verifyAuthToken(req)` + `checkAdminRole(uid)` helper pair.
- **Backend/** — a separate legacy Express server (`weseeyou-backend`), inline Bearer-token
  auth, `strictLimiter` rate limiting.
- **frontend/Backend/** — a stray nested package (accidental copy; a real repo artifact).
- Top-level `firestore.rules` / `storage.rules` (well-written RBAC), `cors.json`, `firebase.json`.

184 source files, largest ~58 KB — well under the 1 MB walker cap. No root `package.json`.

## 1. Tier classification

**Result: `public-facing` (ASVS L2, 70% bar), confidence 1.0, source self-scan.**

Signals that drove it (self-scan path — no Vibe Test handshake present):

| Signal | Weight | Promotes |
|---|---|---|
| deploy config present (`firebase.json`) | strong | public-facing |
| auth/identity dependency (firebase) | medium | public-facing |
| Firestore/Storage security rules | medium | public-facing |
| server-side backend (`functions/`, `Backend/`) | medium | public-facing |
| firebase-admin (server-side user data) | medium | customer-facing-saas |

The classifier landed `public-facing` on 1 strong + 3 medium signals. The lone
customer-facing-saas signal (firebase-admin) was below the promotion threshold
(needs ≥2 medium toward that ceiling), so it nudged confidence but didn't promote.

**Is this right?** Defensible, and arguably one tier light. WSYATM is a multi-user
app with real user accounts, admin roles, persisted PII (a `users` collection with
emails), and a public theater-lobby deployment. A human would reasonably call this
**customer-facing-saas** — it stores and processes other people's data at scale.
The signal-gathering here is the *harness's* heuristic, not a vibe-sec API (the
`classifyTier` engine is pure and correct given its inputs); the gap is that the
"persisted user PII → customer-facing" promotion needs a second medium signal to
fire, and the harness only emitted one. Honest read: the engine did the right thing
with the signals it got; the signal set under-counts WSYATM's data-sensitivity.
The platform fingerprint returned `unknown` (no Next.js/Supabase/Bolt markers —
correct, this is hand-rolled Firebase), so no platform prior elevated anything.

## 4. False-positive assessment

The headline numbers look worse than the app is. The FP rate **exceeds the 12% target.**

### Census of the 24 Band-1 (critical+high) items

| Finding | Verdict |
|---|---|
| 2× service-account private keys | True positive (on-disk; gitignored caveat) |
| `quiz.js:208` unauth LLM endpoint | **True positive** |
| `leaderboards.js:153` unauth LLM endpoint | **False positive** — `generateBadgeIcon` DOES call `verifyAuthToken` + `checkAdminRole` before the Gemini call |
| 5× `Backend/src/index.js` "unauthenticated admin route" | **All 5 false positives** — every one has inline `authHeader.startsWith('Bearer ')` + `auth.verifyIdToken(idToken)` and returns 401 without a token |
| 2× duplicate of the LLM endpoints (`src/games/quiz.js`, `src/social/leaderboards.js`) | Duplicate findings (harness multi-root artifact, see below) |
| 7× `VITE_*` client-bundle key leaks | Mixed — `VITE_GEMINI_API_KEY` is a true positive; `VITE_FIREBASE_API_KEY` (×2) is a soft FP (Firebase web keys are public-by-design) |
| 6× `GOOGLE_API_KEY` (high) | Mixed — the `AIza…` keys are Firebase web keys (public-by-design). Same physical key also surfaces as a low `FIREBASE_WEB_API_KEY` in Band 2 → double-tagged |

### The two FP root causes (both real, both fixable)

**1. The auth heuristics don't recognize Firebase's canonical auth patterns.**
This is the single biggest FP driver. `verifyAuthToken(req)` is *the* auth pattern
across 11 WSYATM function files, and `auth.verifyIdToken(idToken)` is the inline
Express pattern across the Backend admin routes. Neither matches the detectors'
`AUTH_MARKER_RE` / `AUTH_RE` (which look for `verifyToken`, `requireAuth`,
`getServerSession`, `req.user`, `auth(` — but not `verifyAuthToken` or
`verifyIdToken`). Consequences:
   - 5 Backend admin routes flagged "no detectable auth check. Anyone can reach it"
     when they literally return 401 without a Bearer token. **All false.**
   - `generateBadgeIcon` flagged as an *unauthenticated* LLM endpoint when it's
     auth + admin-gated. **Severity inflation** (critical when it's at most a
     "no per-user budget" finding).
   The Express route heuristic also only inspects a **400-char window** after the
   route declaration; WSYATM's inline 401 block pushes the `verifyIdToken` call
   past that window even if the token were in the regex.

**2. Firebase web API keys (`AIza…`) treated as sensitive secrets.**
Firebase web API keys are public-by-design (they identify the project; access is
governed by Firestore rules, which here are solid). The scanner flags them as
`GOOGLE_API_KEY` (high) **and** `FIREBASE_WEB_API_KEY` (low) — so the same key is
double-counted under two pattern names, once in Band 1 and once in Band 2. The
client-key-leak copy hedges well ("if it is one, rename it"), so it's a *soft* FP,
not a hard one — but it still inflates the Band-1 high count.

### FP rate estimate

Of 24 Band-1 items: ~6 hard FPs (5 Backend admin routes + 1 unauth-LLM
mis-severity), ~2 duplicates, ~4 soft FPs (Firebase web keys). Counting hard FPs +
duplicates against the total 49 findings: **roughly 16–25% FP rate — over the 12%
target.** The noise concentrates in **auth-model** (the signature concern — the
worst place for it) and secondarily in **secret-detection** (Firebase-web-key
double-tagging) and the **rate-limiting LLM** severity call.

The high-precision concerns held up well: supply-chain (10/10 accurate),
config-posture (correct true negative on a real rules file), PII-in-logs (accurate).

## 5. Robustness

**Nothing crashed. Zero exceptions across all ten concern detectors over 184 real
source files.** The harness's per-concern guard caught nothing — `errors: []`.
This is the most important result: real-world code shapes (an 8000-line monolith
since modularized, a `.bak` file, a stray nested package, three independent
package.json trees, CommonJS + ESM mixed) did not break the tool.

Specifics:
- Large files (58 KB quiz.js, 55 KB fantasy.js) parsed fine; the 1 MB walker cap
  was never hit.
- `node_modules` correctly skipped in all three trees (PATH_SKIP_REGEX + source-walk
  SKIP_DIR_RE) — no triple-scan of dependencies.
- The complex multi-function `firestore.rules` did **not** false-positive — the
  detector correctly read its RBAC as locked down.
- No git-history edge cases (history scan was off for this read-only run).

### Coverage gaps surfaced (not crashes — blind spots)

- **dependency-cve = 0 / no-op.** Without `osv-scanner` on PATH or network access,
  the in-house dep scan produces nothing. For a real pre-launch audit this concern
  is effectively dark unless the external tool is present. The score still counts it
  as a clean pass (1.0), which is **optimistic** — "we didn't find CVEs" reads the
  same as "we couldn't look." Worth a "scan was a no-op" annotation so the score
  isn't falsely reassuring.
- **piiInventory = 0 fields.** The PII inventory parses Prisma/Drizzle/Zod/Yup
  schemas; WSYATM uses Firestore (schemaless, no schema file), so the signature
  PII-inventory artifact is empty despite a real `users` collection with emails.
  Firestore-shaped PII is invisible to the inventory pass (the PII-in-logs pass
  still caught the emails, so PII isn't entirely missed).
- **config-posture headers/CORS** only reads fixed top-level paths (`server.js`,
  `src/server.ts`, `next.config.*`). In a Firebase Functions app with no root server
  entry, the header/CORS/cookie passes have nothing to read at root — they only
  fired against `Backend/server.js` via the per-subroot loop. A single-root scan
  would miss them.

### Harness artifact (not a vibe-sec bug, but a real-world lesson)

WSYATM is a multi-package repo with no root `package.json`. The manifest-rooted
detectors (deps, supply-chain, config-posture, rate-limiting) read fixed paths
relative to the root they're handed, so the harness ran them against the repo root
**and** each sub-package root, then deduped by finding id. Because the same physical
file gets a different relative path from each root (`functions/src/games/quiz.js`
vs `src/games/quiz.js`), the id differs and dedup misses — producing **3 duplicate
findings** (2 LLM endpoints + 1 in-memory rate-limit store). In the normal
single-root SKILL flow this wouldn't happen, but it's a real lesson: **the
monorepo/multi-package walk strategy needs a path-normalization step** so the same
file isn't double-reported across roots.

## 6. Verdict

**vibe-sec v0.5.0 is close, but not yet acceptance-quality for an unsupervised
pre-launch audit. There is one blocking issue.**

What's genuinely good — and would survive a hard review:
- It found the **real** critical: an unauthenticated Gemini endpoint that can be
  driven to burn money. That's the signature catch, and it landed.
- It found two service-account private keys on disk.
- The supply-chain, PII-in-logs, and config-posture passes were accurate (including
  a correct true negative on a real, complex rules file).
- The tier classifier, weighted score, four-band sort, and gate mechanism all
  worked correctly and produced the right FAIL with the right blocking reasons.
- It did not crash on real-world code. That alone clears a bar fixtures can't test.

The blocking issue:
- **The auth detectors are blind to Firebase's canonical auth patterns
  (`verifyAuthToken`, `auth.verifyIdToken`).** On a Firebase app — a primary
  vibe-coding target — this drives a >12% FP rate concentrated in the *signature*
  concern (auth-model), and it inflates one LLM finding from "needs a budget" to
  "unauthenticated-critical." A builder seeing 5 "anyone can reach your admin
  routes" alarms that are all wrong will lose trust in the whole report — and the
  one real auth gap (the unauth quiz endpoint) gets buried in the false ones. For a
  tool whose differentiator *is* the auth-model concern, false alarms there are the
  worst possible failure mode.

Recommended before a stable promotion (in priority order):
1. **Add `verifyAuthToken`, `verifyIdToken`, and `checkAdminRole`/`checkManagerRole`
   to `AUTH_MARKER_RE` (route-inventory) and `AUTH_RE` (llm-endpoint).** This single
   change kills 5 hard FPs and 1 severity-inflation FP. Widen the Express auth
   window beyond 400 chars, or scan the whole handler body.
2. **Distinguish Firebase web API keys (`AIza…`, public-by-design) from sensitive
   Google keys, and stop double-tagging the same key as both GOOGLE_API_KEY and
   FIREBASE_WEB_API_KEY.**
3. **Annotate dependency-cve when it ran as a no-op** so a 1.0 pass_fraction doesn't
   read as "no CVEs" when it's really "couldn't scan."
4. Path-normalize the multi-package walk so the same file isn't double-reported
   across package roots (harness-level, but the SKILL should own this for monorepos).

None of these are architecture problems — the math substrate, the report layer, the
gate, and the orchestration are all sound and crash-free on a real app. They're
detector-precision fixes, mostly regex additions. Fix #1 is the one that has to land
before this audit is trustworthy on a Firebase app unsupervised. With it, v0.5.x is
acceptance-quality.
