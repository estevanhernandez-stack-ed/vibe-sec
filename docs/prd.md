## This is not a traditional PRD.

Vibe Sec's product requirements are derived during **`/spec`** via the research-swarm + synthesis pattern established in `docs/scope.md`. A traditional Cart PRD anchors on author-intuition about stories + acceptance criteria before research. For Vibe Sec that anchoring would be premature — the 10 security-concern domains are deep enough that pre-research assumptions about user stories would almost certainly get invalidated by the research briefs.

**Where the PRD-equivalents live:**

| Traditional PRD section | Where it actually lives for Vibe Sec |
|---|---|
| Problem statement + users | `docs/scope.md > Idea` + `> Who It's For` |
| Goals + north star | `docs/scope.md > Goals` |
| Epic structure + command surface | `docs/scope.md > What "Done" Looks Like > Command surface` |
| Cross-cutting contracts (handoff, composition, self-evolution, research-swarm orchestration) | `docs/scope.md > Research-swarm architecture` + `> Vibe Test composition (handshake contracts)` + `> Built-in no-account baseline + Pattern #13 expansion path` |
| Confidence + severity + FP policy | `docs/scope.md > Severity + report model` + `> Confidence-tier routing for /vibe-sec:fix` |
| Per-concern stories + acceptance criteria | `docs/research/<concern>.md` × 10 (generated during `/spec` by the research swarm) + `docs/research/synthesis.md` (generated by the synthesis agent) |
| Non-goals | `docs/scope.md > What's Explicitly Cut` |
| First-patient validation | `docs/scope.md > First-patient acceptance bar` (WSYATM tier transition) |

**Why this deviation is architecturally coherent:**

1. **Research-first is load-bearing.** Vibe Sec ships depth in 10 security domains. Most plugin authors know 2-3 well. The research swarm produces the domain intelligence that /prd normally extracts from builder-knowledge. Doing /prd BEFORE research would lock in assumptions research is designed to pressure-test.

2. **Scope.md already carries the PRD structural load.** The six /scope mandatory decisions + 20+ Round 2 deepening decisions concretize everything Cart's /prd skill aims to capture *except* the per-concern story-level AC. The scope doc is ~450 lines; a full PRD would largely restate it with user-story framing.

3. **The synthesis agent substitutes for /prd's story generation.** At `/spec` time, after the 10 research briefs are complete, a synthesis agent produces `docs/research/synthesis.md` — the consolidated per-concern implementation guide. That synthesis includes story-shaped output (what each capability does, under which conditions, with what user-visible behavior). That IS the story+AC layer, produced from evidence rather than intuition.

4. **Cart's /reflect cycle will see the deviation explicitly.** When `/reflect` runs against this project, it'll flag "missing /prd" as a friction-log candidate, at which point we capture this deviation as Pattern #14 wins.jsonl-worthy (an explicit architectural adaptation, not a missed step).

**What `/spec` will do differently as a result:**

- **Phase 1 of /spec becomes the research-swarm dispatch** (10 parallel expert-persona agents × 1 security concern each)
- **Phase 2 is synthesis** (single synthesis agent reads all 10 briefs, produces resolved-conflict synthesis + remaining-conflicts artifact)
- **Phase 3 is traditional /spec work** (stack choices, file structure, architecture diagrams, data flows) — but informed by the research synthesis rather than author-intuition
- **docs/spec.md output** includes both architectural decisions AND per-concern build guidance derived from research

**Open items this stub defers forward:**

- Per-concern user stories + acceptance criteria → generated at `/spec` time in `docs/research/<concern>.md` + synthesis
- Tier × concern applicability matrix → `/spec` time, research-informed
- `findings.jsonl` schema concretization → `/spec` time
- Research-agent prompt-template design → `/spec` first-phase deliverable
- Command consolidation analysis (9 → 7-8) → `/spec` time, informed by research briefs

## The /scope decision log, restated as PRD-style commitments

Pulled forward from `docs/scope.md` for `/spec`'s direct consumption.

**Command surface (router + 8 subcommands = 9 top-level):**
`/vibe-sec` · `/vibe-sec:audit` · `:scan` · `:fix` · `:gate` · `:posture` · `:threat-model` · `:deps` · `:research`

**Classification:** 5 tiers × 5 context modifiers × 10 concerns (matrix generated at `/spec` from research briefs).

**Severity:** Hybrid 4-level (Critical/High/Medium/Low) for Vibe Sec findings + CVSS passthrough for CVE findings. Tier × concern drives severity level.

**FP policy:** 12% across-the-board commitment.

**Report structure:** Four-band — (1) Critical/High actionable now, (2) tier-appropriate educational, (3) graduating-to-next-tier forward-looking, (4) Pattern #13 complement recommendations.

**`/vibe-sec:fix` authority model:** Confidence-tier routing (auto ≥0.90 / stage 0.70–0.89 / inline <0.70) with destructive-action overrides. Never auto-apply: secret rotation, auth logic changes, JWT/session-secret regen. Auto-apply only: `.gitignore` additions, additive security headers.

**Composition contracts:**
- Reads `.vibe-test/state/covered-surfaces.json` when present; falls back to own classification.
- Writes `.vibe-sec/state/findings.jsonl` for Vibe Test to consume at `/vibe-test:generate` time.
- Composes with Vibe Doc for `docs/SECURITY.md` runbook generation.

**v0.2 no-account baseline:** `npm audit` + OSV direct query + own TypeScript secret-regex + own config-file inspectors. Commercial tools (Snyk/Socket/Semgrep/GitGuardian) are Pattern #13 complements surfaced for "future runs."

**First-patient dogfood:** WeSeeYouAtTheMovies at its associate-facing → public-facing tier transition. Real pre-launch hardening stakes; not a synthetic demo.

**Research-swarm orchestration (from Round 2):**
- /spec-time dispatch (not /build)
- 10 parallel expert-persona agents
- Durable `docs/research/<concern>.md` briefs (living docs pattern)
- `/vibe-sec:research --concern <name>` re-runs individual briefs as new information emerges
- Staged synthesis + builder-resolve conflict resolution model (synthesis agent first, then Este adjudicates residual conflicts at `/spec` time)
